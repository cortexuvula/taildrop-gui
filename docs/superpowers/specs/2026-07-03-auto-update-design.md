# Auto-Update Feature — Design

**Date:** 2026-07-03
**Status:** Approved (pending review)
**Motivator:** Users currently have no in-app way to know a new version exists — they must notice releases on GitHub and manually download/reinstall. This design adds automatic update detection (via Tauri's updater plugin, backed by GitHub releases), a non-blocking "update available" notification, and one-click download + install + relaunch.

## Problem

The app has zero update infrastructure today (confirmed by audit):
- No `tauri-plugin-updater` (Rust or JS), no `plugins.updater` config in `tauri.conf.json`.
- No signing keypair — the release workflow doesn't set `TAURI_SIGNING_PRIVATE_KEY`, so no `.sig` artifacts or `latest.json` manifest are produced.
- No version display anywhere in the UI.
- No `@tauri-apps/plugin-process` (needed to relaunch after install).

## Scope

**In scope:**
- Background check for updates on app launch (against GitHub releases `latest.json`).
- Manual "Check for updates" button in Settings (surfaces check errors + "up to date").
- Non-blocking toast notification when an update is available, with a "Download & Install" action.
- Silent background download (signature-verified) with progress shown in the morphing toast.
- "Relaunch now" prompt once the update is downloaded + verified.
- Per-session snooze (dismissed update toast doesn't reappear until next launch or manual recheck).
- Release workflow changes to sign artifacts and emit the manifest.
- Version display in Settings footer.

**Out of scope:** periodic/interval polling (launch-only + manual), staged/phased rollouts, beta/prerelease channels, delta updates, and macOS-Sparkle-style "install on quit" (we do explicit relaunch).

## Decisions (locked during brainstorming)

| Decision | Choice |
|---|---|
| Signing keypair | Generated (no password); pubkey in `tauri.conf.json`, private key as GitHub secret |
| Check trigger | Auto on launch + manual button in Settings |
| Install flow | Silent download (background, signature-verified) + "Relaunch now" prompt |
| Re-check policy | Per-session snooze (dismissed update not re-shown until next launch/manual check) |
| UI surface | Toast-driven (reuses existing `ToastProvider`) |

## Architecture

Six layers, each a clean boundary:

```
┌─ GitHub releases (latest.json manifest + signed artifacts) ─┐
│   ↑ generated by release.yml (signing key added)            │
├─ tauri.conf.json: plugins.updater { endpoints, pubkey } ────┤
│   + bundle.createUpdaterArtifacts: true                      │
├─ Rust: tauri-plugin-updater + tauri-plugin-process ─────────┤
│   (no custom commands — JS plugin API used directly)         │
├─ Frontend: useUpdater hook (check/download/install/relaunch)┤
│   + Settings "Check for updates" button + version display    │
└─ Toast system (extended): persistent update toast w/ actions ┘
```

**Boundary principle:** `useUpdater` is pure logic (mirrors `useTailscale`'s purity). It returns state (`{ status, version, progress, error }`) and actions (`check`, `download`, `install`, `dismiss`). The **component layer** (App + Settings) turns that state into toast calls — same pattern as `onSendError` from the toast feature.

## Components

### 1. Toast extensions (additive, non-breaking)

Two small additions to `src/components/ToastProvider.tsx`. Existing send-failure toasts are unaffected.

```ts
export interface ToastAction {
  label: string;
  onClick: () => void;
}

export interface Toast {
  id: string;
  title: string;
  message?: string;
  variant: ToastVariant;
  durationMs: number;           // 0 = persistent (no auto-dismiss)
  action?: ToastAction;
}
```

- **`action` field:** rendered as a button next to the ✕ in `ToastCard`. Optional; existing toasts without it render unchanged.
- **`durationMs: 0` sentinel:** means "persistent". The `push` function's auto-dismiss timer is skipped when `durationMs === 0`. Existing toasts use the 5000ms default when `durationMs` is unset.
- **`toast.update(id, patch)` method:** mutates an existing toast in place. Lets the update toast morph through its lifecycle (available → downloading → ready) without spawning new toasts. Patch shape: `Partial<Pick<Toast, "title" | "message" | "action">>`. If `patch.action` is omitted, the existing action is cleared (caller must re-supply it explicitly). No-op (returns) if `id` is unknown.
- **`push` signature extended:** `push(variant, title, message?, opts?: { durationMs?: number; action?: ToastAction })`. The existing `error(title, message)` / `info(title, message)` keep working (they call `push` without `opts`).

### 2. The `useUpdater` hook (`src/hooks/useUpdater.ts`)

Pure logic hook — no UI imports. Uses `@tauri-apps/plugin-updater` and `@tauri-apps/plugin-process` directly.

```ts
type UpdateStatus =
  | "idle"          // not checked yet, or last check found nothing, or dismissed
  | "checking"      // network call in flight
  | "available"     // update found, awaiting user action
  | "downloading"   // fetching the signed package
  | "ready"         // downloaded + verified, awaiting relaunch
  | "error";        // something failed (network, verification)

interface UseUpdaterApi {
  status: UpdateStatus;
  version?: string;     // available version (e.g. "0.8.0")
  date?: string;        // release date, when known
  body?: string;        // release notes (markdown), when exposed
  progress?: number;    // 0–100 during "downloading"
  error?: string;       // when status === "error"
  check: () => Promise<void>;        // manual + auto; no-op if already checking
  download: () => Promise<void>;     // available → downloading → ready
  install: () => Promise<void>;      // ready → relaunch
  dismiss: () => void;               // reset to idle (per-session snooze)
}
```

**Lifecycle:**
- `check()` calls `check()` from `@tauri-apps/plugin-updater`. If the returned `update` is non-null, captures `version`/`date`/`body`, sets `status: "available"`. If null, sets `status: "idle"` (up to date). On error (offline, GitHub down, verification), sets `status: "error"` with the message but **does not throw to the caller** — the caller decides whether to surface it.
- `download()` is a no-op unless `status === "available"`. Calls `update.downloadAndInstall({ onEvent })`. The `onEvent` callback updates `progress` during download and sets `status: "ready"` when the event stream signals completion. On error, sets `status: "error"`.
- `install()` is a no-op unless `status === "ready"`. Calls `relaunch()` from `@tauri-apps/plugin-process` — the app quits and reopens on the new version. (Tauri's `downloadAndInstall` already installs the package; `install()` is just the relaunch step.)
- `dismiss()` resets to `status: "idle"` and clears `version`/`progress`. Per-session only — no localStorage (matches the "snooze per-session" decision).

**Auto-check on launch:** the hook runs `check()` once on mount via `useEffect(() => { check(); }, [])`. Result is remembered in state for the session.

**Concurrency guard:** `check()` is a no-op if `status === "checking"`; `download()` is a no-op unless `status === "available"`. Prevents double-calls from rapid button presses.

### 3. App wiring — `useUpdater` state → toasts

`App.tsx` calls `useUpdater()` and translates state transitions into a **single persistent toast** that morphs through the update lifecycle (tracked by `id` in a ref).

```tsx
const updater = useUpdater();
const updateToastId = useRef<string | null>(null);

useEffect(() => {
  if (updater.status === "available") {
    updateToastId.current = toast.info(
      `TailDrop ${updater.version} is available`,
      "Click to download and install the update.",
      { durationMs: 0, action: { label: "Download & Install", onClick: () => updater.download() } },
    );
  } else if (updater.status === "downloading") {
    toast.update(updateToastId.current, {
      title: "Downloading update…",
      message: `${updater.progress ?? 0}%`,
      action: undefined,  // no action during download
    });
  } else if (updater.status === "ready") {
    toast.update(updateToastId.current, {
      title: `Update ready — ${updater.version}`,
      message: "Relaunch to finish installing.",
      action: { label: "Relaunch now", onClick: () => updater.install() },
    });
  } else if (updater.status === "idle" || updater.status === "error") {
    if (updateToastId.current) {
      toast.dismiss(updateToastId.current);
      updateToastId.current = null;
    }
  }
}, [updater.status, updater.progress, updater.version, toast, updater.download, updater.install]);
```

**Auto-check failure handling:** the launch-time `check()` runs silently. If it fails, `status: "error"` is set but App shows **no toast** for auto-check failures (no point nagging on every launch when there's no network). Only the Settings manual button surfaces check errors.

### 4. Settings — manual "Check for updates" + version display

`Settings.tsx` gains a footer with the current version (read at runtime via `getVersion()` from `@tauri-apps/api/app`) and a "Check for updates" button. `App` passes the `updater` API down as a prop.

```tsx
<div className="settings-footer">
  <div className="settings-version">TailDrop v{appVersion}</div>
  <button
    className="btn-secondary"
    onClick={async () => {
      const before = updater.status;
      await updater.check();
      // Surface manual-check results via transient toasts, but only the
      // terminal states (idle = up to date, error = check failed). The
      // "available" case is handled by App's effect (persistent toast), so we
      // do NOT fire a duplicate transient toast here.
      if (updater.status === "idle" && before !== "idle") {
        toast.info("You're up to date", "TailDrop is on the latest version.");
      } else if (updater.status === "error") {
        toast.error("Couldn't check for updates", updater.error);
      }
    }}
    disabled={updater.status === "checking" || updater.status === "downloading"}
  >
    {updater.status === "checking" ? "Checking…" : "Check for updates"}
  </button>
</div>
```

`Settings` calls `useToast()` directly (it's inside `<ToastProvider>`) for the transient "up to date" / "check failed" feedback, keeping that feedback localized to where the user clicked.

### 6. Release workflow (`release.yml`)

Add the signing env vars to all three `tauri-action` steps (macOS, Windows, Linux) so artifacts get signed, and enable `latest.json` generation.

```yaml
# In each of the three tauri-action steps' env: block, add:
TAURI_SIGNING_PRIVATE_KEY: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY }}
TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ${{ secrets.TAURI_SIGNING_PRIVATE_KEY_PASSWORD }}

# In each with: block, add:
updaterJsonPreferWorkspace: true
```

`updaterJsonPreferWorkspace: true` makes tauri-action produce a workspace-format `latest.json` and merge it into the release as the manifest the updater polls.

## Setup checklist (one-time, manual — user does this)

1. **Add the GitHub secret.** Repo Settings → Secrets and variables → Actions → New repository secret:
   - Name: `TAURI_SIGNING_PRIVATE_KEY`
   - Value: the private key generated during brainstorming (provided separately).
2. **Add the password secret** (empty, since the key was generated without a password):
   - Name: `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
   - Value: *(leave empty / blank string)*
3. **Back up the private key** somewhere safe (password manager, etc.). If lost, no future updates can be issued and the pubkey in `tauri.conf.json` would have to be regenerated — breaking updates for everyone on the old key.

The pubkey is already committed in `tauri.conf.json` (Component 5) — it is not secret.

## Security note

The signing key was generated **without a password** for simplicity. Trade-off: if the private key leaks, an attacker could sign a malicious update that the app would accept as valid. Acceptable for this project's current maturity; a future hardening step would rotate to a password-protected key.

## Testing

**Automated gate:** `npx tsc --noEmit` (typecheck) + `npm run build` (production build). No frontend test framework exists (same constraint as the toast feature).

**Manual verification matrix:**

| Scenario | How to trigger | Expected |
|---|---|---|
| Update available (auto) | With a newer GitHub release than installed, launch the app | Persistent toast "TailDrop vX.Y.Z is available" with "Download & Install" button appears within a few seconds |
| Up to date (auto) | Launch with no newer release | No toast; status stays idle |
| Offline at launch | Disconnect network, launch | No toast (auto-check failure is silent); status error internally |
| Manual check, up to date | Settings → "Check for updates" | Transient toast "You're up to date" |
| Manual check, available | Settings → "Check for updates" | Persistent update toast appears (same as auto) |
| Manual check, error | Settings → "Check for updates" while offline | Error toast with the message |
| Download | Click "Download & Install" | Toast morphs to "Downloading… N%" with progress |
| Install | After download, click "Relaunch now" | App quits and reopens on the new version |
| Snooze | Click ✕ on the update toast | Toast dismissed; not re-shown until next launch or manual check |

## Non-goals

- No periodic/interval polling (launch-only + manual).
- No staged/phased rollouts, beta channels, or delta updates.
- No macOS "install on quit" — explicit relaunch only.
- No changes to the existing toast queue-cap behavior (update toasts, being persistent, count toward the cap of 3 like any other toast).
